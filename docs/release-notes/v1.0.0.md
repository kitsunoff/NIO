# v1.0.0 — first release of the current codebase

NIO is a Kubernetes operator that manages NixOS hosts and clusters declaratively:
you describe machines, configurations and clusters as custom resources, and the
operator converges the real hosts to match.

> [!IMPORTANT]
> This is a **restart of the version line**. Earlier tags (`v0.1`–`v1.1.0`) pointed
> at a codebase that has since been rewritten, and at commits that no longer exist
> after a history rewrite. They have been deleted along with their releases. If you
> pinned one of them, move to `v1.0.0`; there is no upgrade path from them because
> there is no shared history to upgrade from.

## What you get

| Kind | What it does |
| --- | --- |
| `Machine` | A host NIO can reach over SSH; reports discoverability and hardware facts |
| `NixosConfiguration` | Converges one host: first-time install, then a day-two cron that keeps it in sync |
| `NixCluster` | Selects Machines into node groups and drives one whole-cluster converge |
| `NixStore` | A shared Nix binary cache other workloads substitute from |
| `NixBuilder` | A remote builder that workloads delegate builds to |
| `NixDeployment`, `NixJob`, `NixCronJob`, `NixStatefulSet` | Run a flake attribute as the corresponding Kubernetes workload |

## Breaking changes and upgrade notes

- **The `Cluster` kind is now `NixCluster`.** Any manifest using `kind: Cluster`
  must be updated.
- **`storeRef` means substituter, not cache.** A `NixStore` referenced without a
  `builderRef` is read-only: nothing is pushed into it. What makes day-two
  converges fast is `builderRef`, and only when that `NixBuilder` has
  `spec.storage` — otherwise its `/nix` is an `emptyDir` that dies with the pod.
- **Delegated builds have no local fallback.** Setting `builderRef` sets
  `max-jobs = 0`, so a builder that cannot produce a member's architecture fails
  the converge instead of merely slowing it. Where NIO can prove the mismatch it
  now refuses up front with `BuilderSystemMismatch` rather than letting the run
  burn its deadline.
- **Status semantics are stricter.** A converge stalled on a missing
  store/builder reports `Blocked` and leaves members at their last known status
  instead of marking them `Failed`; a converge whose runs keep failing reports
  `Degraded` instead of `Ready`; and `Applied` describes the machine rather than the
  most recent run.

## Known limitations

- A converge pod still materialises every member closure in an unbounded
  `emptyDir` `/nix`, even when a builder is used.
- Per-member converge status is coarse: it is derived from the run's outcome, not
  yet parsed from the per-member JSON the converge tool emits.
